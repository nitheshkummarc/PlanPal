# Deployment

PlanPal runs on Supabase (database), Render (API) and Vercel (frontend).

## 1. Database (Supabase)

The schema is described in [DATABASE.md](DATABASE.md).

**New project:** open the SQL editor and run `database/init.sql`. It creates the tables,
constraints, indexes, `updated_at` triggers and default tags, enables the `pg_trgm` extension,
and turns on Row Level Security for every table.

**Existing database (created before 2026-09-29):** run
`database/migrations/001_align_existing_schema.sql` once instead.

1. Take a backup (Database > Backups) or export the tables.
2. Run the duplicate checks listed at the top of the migration. Accounts whose email or
   username differ only by letter case, and tags whose names do, must be merged first.
3. Run the migration. It runs in one transaction, so any error leaves the database unchanged,
   and it is safe to run again.

What it changes is described in its header: interests move from `users.preferences` into
`user_tags`, `events.source_type` and `events.is_active` are dropped, inconsistent prices and
participant counts are repaired, and constraint and index names are made to match `init.sql`.

After either script, confirm in Table Editor that each table shows "RLS enabled". The API
connects as the table owner and is not affected by RLS.

To make a user an administrator:

```sql
UPDATE users SET role = 'admin' WHERE email = 'you@example.com';
```

## 2. API (Render)

`render.yaml` defines the service. Set these environment variables in the Render dashboard:

| Variable | Value |
| --- | --- |
| `SUPABASE_DATABASE_URL` | Supabase pooler connection string |
| `ALLOWED_ORIGINS` | The Vercel URL, e.g. `https://planpal-silk.vercel.app` |
| `SECRET_KEY`, `JWT_SECRET_KEY` | Generated by Render |
| `ENABLE_TASK_SCHEDULER` | `true` |
| `REDIS_URL` | Optional; needed only when running more than one worker |

Render checks `/api/system/ready` before routing traffic to a new deploy. The API refuses to
start in production if a required variable is missing.

Tokens issued before this release keep working (they have no `token_version` claim, which is
treated as version 0) until they expire.

## 3. Frontend (Vercel)

- Root directory: `frontend`
- Build command: `npm run build` (type-checks, then builds)
- Environment variable: `VITE_API_BASE_URL` = the Render URL, e.g. `https://planpal-backend-wcsc.onrender.com`

`vercel.json` rewrites every path to `index.html` for client-side routing and sets the
security headers.

## 4. Running the containers locally (optional)

`docker-compose.local.yml` builds the API and an nginx-served frontend that proxies `/api/`
to the API, using the Supabase database from `backend/.env`:

```bash
docker compose -f docker-compose.local.yml up --build     # http://localhost:3000
```

## 5. Rolling back

- Render and Vercel: redeploy the previous deployment from their dashboards.
- Database: restore the backup taken in step 1. The migration cannot be reversed
  automatically because it drops columns.
